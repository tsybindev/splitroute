## 1. Проблема и видение

Полнотуннельный VPN решает задачу «спрятать весь трафик», но ломает повседневную работу: локальные сервисы (`localhost`, Docker), банки и госуслуги, корпоративные ресурсы и умный дом начинают ходить через удалённый сервер. Пользователь вынужден постоянно включать и выключать VPN либо вручную настраивать прокси в каждом приложении.

**Видение.** Клиент, в котором пользователь один раз выбирает приложения (браузер, Telegram, терминал, конкретные CLI-утилиты), и дальше только эти приложения ходят через прокси. Всё остальное — напрямую, без изменения привычек и без «сломанного интернета».

**Позиционирование.** Подключение и каталог локаций — как в Happ; выбор приложений — как в FlClash; аккуратный трей и настройки — как в Clash Verge Rev. Отличие: allowlist приложений является главным сценарием, а не дополнительной функцией.

## 2. Цели и не-цели

### Цели MVP

1. Пользователь добавляет подписку, выбирает локацию и подключается за три действия.
2. Пользователь выбирает приложения, трафик которых идёт в прокси; трафик остальных приложений не попадает в туннель.
3. Клиент живёт в трее: подключение/отключение, статус, автозапуск, выход.
4. Установка и работа не требуют терминала и ручного редактирования конфигов.
5. Одинаковое поведение на macOS, Windows и Linux в рамках возможностей платформы (см. §10).

### Не-цели MVP

- Мобильные платформы (Android/iOS) и App Store.
- Полнотуннельный режим по умолчанию.
- Kill switch как обязательная функция MVP: при падении ядра выбранные приложения временно отпускаются напрямую (fail-open), клиент это детектирует, переподключается и предупреждает. Kill switch — v0.2 (см. §13).
- Поддержка произвольных форматов подписок: принимаются Happ-совместимый JSON и base64-список `vless://`-ссылок; Clash YAML и прочие форматы — нет.
- Собственные rule-set'ы, блокировка рекламы, каскадные прокси, мультихоп.
- Несколько одновременных VPN-подключений и одновременная работа с другим VPN-клиентом.

## 3. Пользователи и сценарии

**Основной пользователь** — технически грамотный человек, у которого есть подписка на VLESS/Reality, и которому нужен выборочный прокси без ручной настройки каждого приложения.

Сценарии:

1. **Браузер + Telegram через прокси, остальное напрямую.** Пользователь отмечает Chrome и Telegram, подключается к Нидерландам. Банк, Ozon и локальная сеть продолжают работать напрямую.
2. **Терминал и CLI.** Пользователь отмечает `git`, `curl`, `docker` (или каталог `/opt/homebrew/bin`), чтобы `git push` и `curl` шли через прокси, а остальные процессы — напрямую.
3. **Быстрое переключение.** Пользователь сворачивает окно в трей, переключает локацию и видит статус без открытия приложения.
4. **Диагностика.** Что-то не работает: пользователь открывает логи, копирует диагностику и видит, какой процесс не сматчился или какая ошибка пришла от подписки.

## 6. Функциональные требования

### 6.1. Подписка и профили (M1, M2)

- Формат MVP: Happ-совместимый JSON — массив полных Xray-конфигов. Каждый элемент содержит `remarks`, `inbounds`, `outbounds`, `routing`, `dns`, `burstObservatory`.
- Дополнительно принимается base64-список `vless://`-ссылок: провайдеры отдают его для не-Happ User-Agent. Формат определяется автоматически по телу ответа: JSON — предпочтительный, ссылки — совместимый вариант. Из ссылки берутся UUID, сервер, порт, Reality/TLS (`pbk`, `sid`, `sni`, `fp`, `alpn`), `flow` и транспорт; записи с неподдерживаемым транспортом или security пропускаются с причиной, как и в JSON.
- User-Agent по умолчанию — собственный `SplitRoute/0.1.0`; с ним провайдер отдаёт base64-список (быстрее и стабильнее). `Happ/4.1.0` остаётся доступным значением для провайдеров, отдающих JSON.
- Запрос выполняется с заголовками `User-Agent`, `X-HWID`, `Accept: application/json`. Значения по умолчанию соответствуют рабочему скрипту, но редактируются в настройках.
- HWID генерируется один раз при первом запуске: 16 hex-символов из CSPRNG, хранится локально и отправляется в `X-HWID`. Он не выводится из серийных номеров, MAC-адресов и других аппаратных идентификаторов — провайдеру нужен стабильный идентификатор устройства, а не «железо». Ручное редактирование и перенос HWID доступны в настройках: провайдер может привязывать подписку к устройству, и смена HWID способна сбросить привязку.
- Из профиля берётся outbound с тегом `proxy`. Профили без него пропускаются с предупреждением, а не роняют обновление.
- Внутренняя модель `Profile`: `id`, `name (remarks)`, `protocol`, `server`, `port`, `uuid`, `flow`, `tls` (`reality`/`tls`, SNI, public key, short id, fingerprint, ALPN), `transport` (`tcp`/`ws`/`grpc`/`http`), `raw` (исходный JSON только в кэше).
- Текущая подписка отдаёт профили `VLESS + Reality + TCP`. Это обязательный набор MVP. Остальные протоколы и транспорты (включая hysteria) отображаются, но могут быть помечены «не поддерживается в этой версии» — без падения парсера.
- Секреты (URL подписки, HWID) хранятся только в пользовательском конфиге приложения и никогда не попадают в git и в экспортируемую диагностику.
- Ошибки: нет сети, HTTP 401/403/404, невалидный JSON, неизвестный формат ответа, пустой список профилей — каждая с отдельным понятным сообщением и кнопкой «повторить».
- Загрузка подписки не блокирует интерфейс: HTTP-запрос выполняется вне главного потока, общий таймаут — 45 с, подключение — 10 с (провайдеры могут отвечать десятки секунд). Сохранённый в старых `state.json` UA `SplitRoute/0.1.0` продолжает работать без миграции: для него сервер отдаёт base64-список, который теперь поддерживается; выбранный пользователем UA не перезаписывается.

### 6.2. Подключение и маршрутизация (M3, M5)

- Ядро — sing-box, запускается только привилегированным helper'ом как отдельный процесс. UI не получает root.
- TUN-интерфейс: `auto_route: true`, `strict_route: true`, MTU по умолчанию 1500 (настраивается), стек `mixed`.
- Политика IPv6: по умолчанию IPv6 в туннель не заворачивается и блокируется для выбранных приложений, чтобы избежать утечек и «полурабочих» сайтов. Переключатель в настройках.
- Обход: `localhost`, приватные диапазоны (`10/8`, `172.16/12`, `192.168/16`, `fd00::/8`), link-local и multicast всегда идут напрямую.
- При активном другом VPN/TUN-интерфейсе клиент предупреждает о конфликте и предлагает отключиться, а не молча ломает сеть.
- При выходе приложения и при выключении туннеля helper гарантированно останавливает sing-box и удаляет TUN-интерфейс; «зависших» процессов и маршрутов не остаётся.
- Поведение при падении ядра: TUN исчезает, и трафик выбранных приложений может уйти напрямую (fail-open). Клиент детектирует это, показывает предупреждение и делает до 3 попыток переподключения. Kill switch (fail-closed) — v0.2.
- Внутренний DNS sing-box работает через TUN; политика DNS описана в §6.4.
- Конфиг, который получает helper: генерируется приложением, проходит `sing-box check`, пишется в root-каталог и удаляется при остановке.

### 6.3. Allowlist приложений (M4) — ключевая функция

**Честное определение.** Маршрутизация выполняется по процессу — владельцу сокета, а не по «приложению» в пользовательском смысле. Поэтому:

- `curl`, запущенный в Terminal, матчится как `curl`, а не как `Terminal`. Чтобы пустить через прокси все CLI-утилиты, нужно добавить конкретные бинари или правило по каталогу (например, `/opt/homebrew/bin/*`).
- Браузер создаёт несколько процессов (helper'ы), которые тоже делают сетевые соединения. Поэтому для браузеров используется правило по пути внутри `.app` (macOS) или по каталогу установки (Windows/Linux), а не только имя процесса.
- Приложения внутри Flatpak/Snap на Linux могут иметь путь внутри sandbox; такие правила помечаются как «может не сработать» и проверяются вручную.

**Модель правила.**

```json
{
  "id": "rule-chrome",
  "name": "Google Chrome",
  "platform": "macos",
  "process_name": ["Google Chrome", "Google Chrome Helper"],
  "process_path": ["/Applications/Google Chrome.app/Contents/MacOS/Google Chrome"],
  "path_regex": ["^/Applications/Google Chrome\\.app/"],
  "enabled": true
}
```

Используются те поля, которые поддерживает ядро на текущей ОС; `path_regex` — предпочтительный вариант для браузеров, `process_name` — для простых случаев и CLI.

| ОС | Основной идентификатор | Как получаем | Нюанс |
|---|---|---|---|
| macOS | абсолютный путь внутри `.app` | `NSRunningApplication`, обход `/Applications`, `/System/Applications`, `~/Applications` | helper-процессы требуют regex по каталогу `.app` |
| Windows | полный путь `.exe` | перечисление процессов, реестр, ярлыки Start Menu | Store-приложения (AppX) — после MVP; пути могут отличаться у разных установок |
| Linux | путь из `/proc/<pid>/exe` | `/proc`, `.desktop`-файлы | Flatpak/Snap — sandbox-пути; Wayland на матчинг не влияет |

- UI: вкладки «Запущенные / Установленные / Все правила». «Установленные» — каталог приложений ОС (v0.2, S4-T1): macOS — `.app` в `/Applications`, `/System/Applications`, `~/Applications` (один уровень); Linux — `.desktop` (путь из `Exec`); Windows — ярлыки «Пуск» и записи `Uninstall` с `DisplayIcon`. Поиск по имени, действие «Добавить правило» создаёт **выключенное** правило: macOS — `path_regex` по каталогу `.app`, Windows/Linux — `process_path`. Иконки (S4-T2) приходят отдельной командой `app_icon(app)` как готовый data URL: macOS — PNG-чанк из `.icns`, Linux — `Icon=` из `.desktop` с поиском в `hicolor`, Windows — ресурс `.exe`; изображение нормализуется до 64 px, кэшируется в памяти по пути. UI грузит иконку лениво по появлению строки и при её отсутствии показывает заглушку с первой буквой имени (не блокирует список и не читает диск на каждый рендер). «Запущенные» до появления источника процессов показывает пояснение-заглушку. Ручное добавление пути — на вкладке «Все правила»; переключатель на каждое правило.
- Валидация: если путь не существует или процесс не найден, правило сохраняется, но помечается «неактивно» с подсказкой (отметка сохранённых правил — backlog; каталог отбрасывает записи с отсутствующим `Exec` уже при сканировании).
- UI показывает итоговый сгенерированный конфиг (без секретов) — для доверия и отладки.

### 6.4. DNS

- Цель: не допускать молчаливых утечек DNS выбранных приложений и дать пользователю выбор между приватностью и совместимостью.
- **Разделение DNS по процессу (бывший вариант по умолчанию) не поддерживается.** На macOS 15.8.2 / sing-box 1.14.4 DNS-правила с `process_name`/`process_path` для TUN не матчатся: `dns/tls[remote]` остаётся unreferenced, DNS выбранного приложения уходит в локальный resolver. Проверено 2026-11-12, подробности — `docs/research.md` §9. `hijack-dns` и `sniff` это не исправляют.
- **Пользователь выбирает один из двух режимов** в настройках; по умолчанию — `proxy`:
  - **`proxy` — весь DNS через прокси.** В sing-box остаются `remote` (DoT через `proxy`) и `local` (системный); включён `hijack-dns` для порта 53, `dns.final = remote`. Утечек нет, но DNS невыбранных приложений тоже идёт через прокси, а локальные имена (`.local`, captive portal) могут требовать отдельного правила `local`. Remote DoT через прокси проверен 2026-11-12.
  - **`system` — системный DNS для всех.** В конфиге только `local`, без `remote` и DNS-правил. Максимально совместимо, но DNS выбранных приложений уходит в локальный resolver; в UI показывается предупреждение.
- В UI: переключатель режима, короткое объяснение последствий каждого и предупреждение для `system`; в логах — выбранный режим и риск утечки для `system`. Молчаливых утечек быть не должно.
- Отдельный пункт проверки: DNS через TUN при активном `systemd-resolved` на Linux и при включённом Private Relay на macOS; локальные домены в режиме `proxy`.

### 6.5. Трей, автозапуск, окно (M6)

- Трей: иконка отражает состояние (отключено / подключение / подключено / ошибка), меню — статус, локация, подключить/отключить, открыть, выход.
- Закрытие окна сворачивает в трей (настраивается). Выход из трея корректно останавливает ядро и helper-сессию.
- Автозапуск: Tauri autostart plugin; опции «запускать свёрнутым» и «подключаться при старте».
- Single instance: повторный запуск открывает существующее окно.

### 6.6. Настройки (M8)

- Подписка: URL, HWID, User-Agent, интервал автообновления, «обновить сейчас».
- Сеть: MTU, IPv6 (вкл/выкл), локальный mixed-inbound (вкл/выкл, порт по умолчанию 10808), DNS-режим: `proxy` (весь DNS через прокси, по умолчанию) или `system` (DNS ОС, с предупреждением об утечке).
- Приложение: язык интерфейса (русский/английский, применяется без перезапуска), автозапуск, старт свёрнутым, автоподключение, уровень логов, папка логов.
- Язык — часть пользовательских настроек: `preferences.language` (`ru` по умолчанию) в `state.json`. Отсутствующее поле читается как `ru`, неизвестное значение — тоже `ru`, чтобы ручная правка файла не сбрасывала остальные настройки. Источник истины — Rust (AGENTS §10.8); UI переключает язык через `settings_update` и применяет его без перезапуска окна.
- Helper: статус (установлен / не установлен / устарел / не отвечает) с версией ядра, «установить»/«переустановить», «удалить». Ошибка установки показывается с конкретной причиной: нужны права, операция отменена, не найден бинарь, платформа не поддерживается. Пароль администратора запрашивает система, приложение его не хранит.
- Сброс настроек и очистка кэша подписки.

### 6.7. Логи и диагностика (M9)

- Просмотр последних N строк логов приложения и ядра, фильтр по уровню, автоскролл.
- «Копировать диагностику»: версия приложения, ОС, архитектура, версия sing-box, статус helper'а, выбранная локация, тип ошибки; без URL подписки, HWID и UUID.
- Ротация логов, ограничение размера.

### 6.8. Права и helper (M7)

- Первый запуск без helper'а: приложение работает в ограниченном режиме (подписка, настройки, список приложений), подключение недоступно.
- Установка helper'а — отдельный экран с объяснением, зачем нужны права, и одной кнопкой. Требуется пароль администратора / UAC / polkit; пароль вводится в системном диалоге и приложением не хранится.
- Если установка не удалась, UI показывает код и точную причину от установщика (`RequiresPrivileges`, отмена пользователем, отсутствующий бинарь, неподдерживаемая платформа), а не общую строку. Статус после действия берётся только из `helper_status`.
- Удаление helper'а — из настроек, полностью очищает сервис, сокет и runtime-файлы.
- Протокол helper'а: только `install`, `uninstall`, `start`, `stop`, `status`. Никаких произвольных команд и путей. Конфиг проверяется `sing-box check` до запуска.

## 13. Принятые решения и открытые вопросы

### Принято

1. **Название — SplitRoute.** Идентификаторы пакетов и сервисов: `splitroute`. Финальные bundle id и домены фиксируются перед первой публичной сборкой.
2. **Лицензия — GPL-3.0.** Файл `LICENSE` в корне; сторонние компоненты и их лицензии — в `THIRD_PARTY_NOTICES` в корне. Оба файла входят в каждую сборку: macOS/Windows — ресурсы приложения, `.deb`/`.rpm`/AppImage — `/usr/share/doc/splitroute/`; DMG и NSIS показывают текст лицензии при установке. sing-box (GPL-3.0) поставляется как отдельный процесс без патчей, со ссылкой на исходники закреплённой версии.
3. **HWID — стабильный случайный идентификатор установки.** 16 hex-символов из CSPRNG, генерируется при первом запуске, хранится локально, отправляется в `X-HWID`, редактируется в настройках. Не строится из аппаратных серийников и MAC-адресов. Провайдер использует его как идентификатор устройства; смена HWID может сбросить привязку подписки.
4. **Kill switch — не в MVP.** В allowlist-режиме риск утечки при падении ядра признан (R13), но реализация fail-closed требует отдельных механизмов на каждой ОС. В MVP: детект падения, до 3 попыток переподключения и явное предупреждение. Kill switch — v0.2.
5. **DNS — два пользовательских режима.** Per-process DNS не поддерживается на macOS 15 / sing-box 1.14 (проверено 2026-11-12). Пользователь выбирает `proxy` (весь DNS через прокси, по умолчанию, без утечек) или `system` (DNS ОС, совместимо, но с предупреждением об утечке). Старый режим `process` выводится из UI и мигрирует в `proxy`.

### Открыто

1. **IPv6.** Базовое решение — в MVP выключен (см. §6.2). После spike решить, нужна ли маршрутизация IPv6 для выбранных приложений.
2. **Доменные правила провайдера.** Переносить ли `geoip:ru`/`geosite:*` из шаблона скрипта в MVP (конфликтует с идеей «выбранное приложение целиком в прокси»)?
3. **Финальные идентификаторы.** Bundle id macOS, имя службы Windows, имя systemd-юнита и домены обновлений — до первой публичной сборки.

## Приложение A. Техническое исследование (кратко)

Полные ссылки и даты проверки — в [docs/research.md](./docs/research.md).

- sing-box поддерживает `process_name`, `process_path`, `process_path_regex` на Linux, Windows и macOS. Это основа per-app без своего packet-стека.
- Официальный Apple-клиент sing-box (SFM) не даёт process-правил из-за ограничений NetworkExtension; CLI-ядро с правами — даёт.
- На macOS 27 у не-Apple-подписанных бинарей чтение `pcblist` через sysctl возвращает только заголовок → process-правила не матчатся. Это главный риск архитектуры (R1).
- «Правильный» per-app на macOS — NetworkExtension (Packet Tunnel/App Proxy), требует entitlement и Apple Developer Program; переносим на этап 5.
- Текущая подписка: 2 профиля, оба `VLESS + Reality + TCP`; в outbound'ах также есть `direct`, `block`, `fragment-out`, в профиле — `burstObservatory`.
- Окружение разработки на текущей машине: macOS 15.8.2 arm64, Xcode CLT есть, Node 22 и pnpm есть, Rust отсутствует (устанавливается по AGENTS.md).
