## 1. Проблема и видение

Полнотуннельный VPN решает задачу «спрятать весь трафик», но ломает повседневную работу: локальные сервисы (`localhost`, Docker), банки и госуслуги, корпоративные ресурсы и умный дом начинают ходить через удалённый сервер. Пользователь вынужден постоянно включать и выключать VPN либо вручную настраивать прокси в каждом приложении.

**Видение.** Клиент, в котором пользователь один раз выбирает приложения (браузер, Telegram, терминал, конкретные CLI-утилиты), и дальше только эти приложения ходят через прокси. Всё остальное — напрямую, без изменения привычек и без «сломанного интернета».

**Позиционирование.** Подключение и каталог локаций — как в Happ; выбор приложений — как в FlClash; аккуратный трей и настройки — как в Clash Verge Rev. Отличие: allowlist приложений является главным сценарием, а не дополнительной функцией.

## 2. Цели и не-цели

### Цели MVP

1. Пользователь добавляет подписку, выбирает локацию и подключается за три действия.
2. Пользователь выбирает приложения, трафик которых идёт в прокси; трафик остальных приложений не попадает в туннель.
3. Клиент живёт в трее: подключение/отключение, статус, автозапуск, выход.
4. Установка и работа не требуют терминала и ручного редактирования конфигов.
5. Одинаковое поведение на macOS, Windows и Linux в рамках возможностей платформы (см. §10).

### Не-цели MVP

- Мобильные платформы (Android/iOS) и App Store.
- Полнотуннельный режим по умолчанию.
- Kill switch как обязательная функция MVP: в v0.1 при падении ядра выбранные приложения временно отпускаются напрямую (fail-open), клиент это детектирует, переподключается и предупреждает. В v0.2 добавлен opt-in fail-closed для macOS (pf), Linux (nftables) и Windows (WFP); рантайм Windows ещё не проверялся (см. §6.2, §13).
- Поддержка произвольных форматов подписок: принимаются Happ-совместимый JSON и base64-список `vless://`-ссылок; Clash YAML и прочие форматы — нет.
- Собственные rule-set'ы, блокировка рекламы, каскадные прокси, мультихоп.
- Несколько одновременных VPN-подключений и одновременная работа с другим VPN-клиентом.

## 3. Пользователи и сценарии

**Основной пользователь** — технически грамотный человек, у которого есть подписка на VLESS/Reality, и которому нужен выборочный прокси без ручной настройки каждого приложения.

Сценарии:

1. **Браузер + Telegram через прокси, остальное напрямую.** Пользователь отмечает Chrome и Telegram, подключается к Нидерландам. Банк, Ozon и локальная сеть продолжают работать напрямую.
2. **Терминал и CLI.** Пользователь отмечает `git`, `curl`, `docker` (или каталог `/opt/homebrew/bin`), чтобы `git push` и `curl` шли через прокси, а остальные процессы — напрямую.
3. **Быстрое переключение.** Пользователь сворачивает окно в трей, переключает локацию и видит статус без открытия приложения.
4. **Диагностика.** Что-то не работает: пользователь открывает логи, копирует диагностику и видит, какой процесс не сматчился или какая ошибка пришла от подписки.

## 6. Функциональные требования

### 6.1. Подписка и профили (M1, M2)

- Формат MVP: Happ-совместимый JSON — массив полных Xray-конфигов. Каждый элемент содержит `remarks`, `inbounds`, `outbounds`, `routing`, `dns`, `burstObservatory`.
- Дополнительно принимается base64-список `vless://`-ссылок: провайдеры отдают его для не-Happ User-Agent. Формат определяется автоматически по телу ответа: JSON — предпочтительный, ссылки — совместимый вариант. Из ссылки берутся UUID, сервер, порт, Reality/TLS (`pbk`, `sid`, `sni`, `fp`, `alpn`), `flow` и транспорт; записи с неподдерживаемым транспортом или security пропускаются с причиной, как и в JSON.
- Дополнительно принимается Clash YAML (mihomo/Clash.Meta): YAML-отображение с ключом `proxies`, включая JSON-нотацию (YAML — надмножество JSON) и flow-стиль. Конвертируются только узлы `type: vless` с `network: tcp` и Reality (`reality-opts.public-key`/`short-id`) или TLS (`servername`, `client-fingerprint`, `alpn`); узлы других типов (`ss`, `vmess`, `trojan`, `hysteria2` и др.), транспорты не-TCP, `tls: false` и `skip-cert-verify: true` пропускаются с причиной, не роняя обновление. Дискриминатор формата у провайдера — User-Agent подписки.
- User-Agent по умолчанию — собственный `SplitRoute/0.1.0`; с ним провайдер отдаёт base64-список (быстрее и стабильнее). `Happ/4.1.0` остаётся доступным значением для провайдеров, отдающих JSON.
- Запрос выполняется с заголовками `User-Agent`, `X-HWID`, `Accept: application/json`. Значения по умолчанию соответствуют рабочему скрипту, но редактируются в настройках.
- HWID генерируется один раз при первом запуске: 16 hex-символов из CSPRNG, хранится локально и отправляется в `X-HWID`. Он не выводится из серийных номеров, MAC-адресов и других аппаратных идентификаторов — провайдеру нужен стабильный идентификатор устройства, а не «железо». Ручное редактирование и перенос HWID доступны в настройках: провайдер может привязывать подписку к устройству, и смена HWID способна сбросить привязку.
- Из профиля берётся outbound с тегом `proxy`. Профили без него пропускаются с предупреждением, а не роняют обновление.
- Внутренняя модель `Profile`: `id`, `name (remarks)`, `protocol`, `server`, `port`, `uuid`, `flow`, `tls` (`reality`/`tls`, SNI, public key, short id, fingerprint, ALPN), `transport` (`tcp`/`ws`/`grpc`/`http`), `raw` (исходный JSON только в кэше).
- Текущая подписка отдаёт профили `VLESS + Reality + TCP`. Это обязательный набор MVP. Остальные протоколы и транспорты (включая hysteria) отображаются, но могут быть помечены «не поддерживается в этой версии» — без падения парсера.
- Секреты (URL подписки, HWID) хранятся только в пользовательском конфиге приложения и никогда не попадают в git и в экспортируемую диагностику.
- Ошибки: нет сети, HTTP 401/403/404, невалидный JSON, неизвестный формат ответа, пустой список профилей — каждая с отдельным понятным сообщением и кнопкой «повторить».
- Загрузка подписки не блокирует интерфейс: HTTP-запрос выполняется вне главного потока, общий таймаут — 45 с, подключение — 10 с (провайдеры могут отвечать десятки секунд). Сохранённый в старых `state.json` UA `SplitRoute/0.1.0` продолжает работать без миграции: для него сервер отдаёт base64-список, который теперь поддерживается; выбранный пользователем UA не перезаписывается.
- **Импорт по QR (этап 8).** Подписку можно добавить из QR-кода: картинка приходит из выбранного файла, перетаскиванием в окно или вставкой скриншота (Cmd+V). Декодирование выполняется локально в Rust (`rqrr`): команды `qr_decode_image` (base64-тело картинки от вебвью) и `qr_decode_file` (путь от drag-drop), обе асинхронные, без новых привилегий и плагинов. Распознаются прямая `http(s)`-ссылка на подписку с непустым хостом и Happ-обёртка `happ://add?url=…` / `happ://add/…` (значение — base64 standard/url-safe с паддингом или без, затем процентное декодирование); результат префилл-ит обычную форму добавления подписки, имя и параметры пользователь дозаполняет сам. QR со списком `vless://`-ссылок и нераспознанный текст дают отдельные понятные ошибки: импорт узлов без подписки не поддерживается, модель подписки требует URL. Найденных QR на картинке может быть несколько — берётся первая распознанная ссылка. Декодированное содержимое нигде не логируется (URL — секрет).
- **Несколько подписок (этап 6).** Подписки — независимые записи в `state.json` (`subscriptions`): у каждой свои имя, URL, User-Agent, интервал автообновления, кэш последнего успешного ответа и время загрузки. HWID — общий для всех подписок (это идентификатор устройства, а не подписки). Активная локация — одна на всё приложение: идентификатор профиля вычисляется из содержимого (имя, сервер, порт, UUID), поэтому коллизия между подписками означает буквально одинаковые профили. Смена URL подписки сбрасывает её кэш; удаление подписки не затрагивает активный туннель и сбрасывает выбор только если профиль исчез отовсюду. Устаревший `state.json` с единственной подпиской (URL в `settings.subscription`, общий список профилей) при первом чтении переносится в первую запись и сразу записывается в новом формате. Добавление подписки выполняется в «Настройках» (`subscription_add`); «Локации» группируются по подпискам в порядке добавления, у каждой группы своё время обновления и кнопка «Обновить».
- **Автообновление подписки (M1).** Пока приложение запущено, каждая подписка обновляется в фоне раз в свои `auto_update_hours` часов; `0` выключает автообновление этой подписки. Расписание считается от последней успешной загрузки записи (`fetched_at`) и последней попытки: если попытка была позже, отсчёт идёт от неё. Первая попытка выполняется при запуске, если данных ещё нет или интервал истёк. Ручное «обновить сейчас» использует то же расписание: успешная загрузка переносит следующий момент на полный интервал, неудачная — тоже (недоступный провайдер не опрашивается на каждой проверке). Ошибка сети не стирает кэш последнего успешного ответа и не меняет выбранную локацию; причина пишется в лог одной строкой `WARN` без адресов. На одну подписку выполняется не больше одной загрузки: параллельный запрос к ней получает код `FETCH_IN_PROGRESS`, а планировщик в этом случае просто пропускает тик; обновления разных подписок друг другу не мешают. Планировщик живёт на `tauri::async_runtime` (новых зависимостей нет), раз в минуту обходит все подписки и при успехе отправляет событие `subscription-updated` с данными одной подписки, по которому UI обновляет её группу без перезагрузки окна. «Следующее обновление» вычисляется из `fetched_at` записи и её интервала и отдаётся UI полем `next_update_at` в `subscriptions_list`/`profiles_list`/`subscription_fetch`.
- **Проверка задержки локаций (M2).** Задержка измеряется TCP-connect до `server:port` профиля из непривилегированного приложения: ядро не запускается, helper не участвует, UUID и TLS-параметры не используются. Это задержка установления TCP-соединения, а не скорость прокси: рукопожатие TLS/Reality и перегрузка сервера в число не входят. Таймаут TCP-connect — 3 с; разрешение имени выполняет системный resolver и отдельным таймаутом не ограничено (при зависшем resolver проверка может быть дольше). Лимит — 64 профиля, одновременно не больше 8 замеров; команда асинхронная и не блокирует окно. Ошибка сети — типизированный код (`PING_TIMEOUT`, `PING_UNREACHABLE`, `PING_DNS`); в логах только имя локации и число задержки, адреса серверов не пишутся.
- **Автовыбор и автопереключение (v0.2).** Автовыбор выбирает локацию с минимальной задержкой после проверки; автопереключение следит за текущей локацией при активном подключении. По умолчанию обе функции выключены. Порог деградации — 100 мс (новая локация должна быть быстрее не меньше чем на эту величину), интервал проверки — 60 с, подтверждений подряд — 2, неудачных замеров до переключения — 2. Переключение — только по явно включённой настройке: `stop` → выбор локации → `start` с тем же флагом kill switch; если новый старт не удался, приложение пытается вернуться к прежней локации, чтобы не оставить сеть без туннеля и правил. Без успешного замера хотя бы одной альтернативы переключение не выполняется.

### 6.2. Подключение и маршрутизация (M3, M5)

- Ядро — sing-box, запускается только привилегированным helper'ом как отдельный процесс. UI не получает root.
- TUN-интерфейс: `auto_route: true`, `strict_route: true`, MTU по умолчанию 1500 (настраивается), стек `mixed`.
- Политика IPv6: по умолчанию IPv6 в туннель не заворачивается и блокируется для выбранных приложений, чтобы избежать утечек и «полурабочих» сайтов. Переключатель в настройках.
- Обход: `localhost`, приватные диапазоны (`10/8`, `172.16/12`, `192.168/16`, `fd00::/8`), link-local и multicast всегда идут напрямую.
- При активном другом VPN/TUN-интерфейсе клиент предупреждает о конфликте и предлагает отключиться, а не молча ломает сеть.
- При выходе приложения и при выключении туннеля helper гарантированно останавливает sing-box и удаляет TUN-интерфейс; «зависших» процессов и маршрутов не остаётся.
- Поведение при падении ядра: TUN исчезает, и трафик выбранных приложений может уйти напрямую (fail-open). Клиент детектирует это, показывает предупреждение и делает до 3 попыток переподключения. Для защиты от утечки есть **opt-in kill switch (fail-closed)**, см. ниже.
- **Kill switch (fail-closed).** Настройка `network.kill_switch` в `state.json`, по умолчанию выключена (старые файлы читаются как `false`). При включении helper ставит правила firewall **до** запуска ядра и снимает их только при `stop`, выходе приложения или выключении настройки. При падении ядра правила остаются, поэтому прямой трафик не выходит мимо туннеля.
  - **Что блокируется.** Правила разрешают loopback, локальные сети (`10/8`, `172.16/12`, `192.168/16`, `169.254/16`, multicast, IPv6 link-local/ULA/multicast) и трафик ядра — на Unix это uid 0, на Windows эквивалент — точный AppId процесса `sing-box.exe`. На Windows дополнительно разрешается трафик, у которого локальный адрес соединения равен адресу TUN: так приложения ходят в туннель, а при исчезновении TUN это условие перестаёт совпадать. DHCP-клиент (`UDP 68 → 67`) разрешён отдельно, иначе аренда адреса не продлевается. Всё остальное блокируется. Это шире, чем allowlist: per-process firewall на macOS (pf) недоступен, поэтому при мёртвом туннеле прямой выход прекращается у всех непривилегированных процессов, а не только у выбранных. Локальная сеть и DNS к локальному resolver остаются доступны — это осознанное исключение.
  - **Механизмы.** macOS — pf anchor `com.apple/splitroute.killswitch` (системный `/etc/pf.conf` уже содержит `anchor "com.apple/*"`; `pfctl -E` включается helper'ом, токен хранится в runtime-каталоге `0600`). Linux — отдельная таблица nftables `inet splitroute_killswitch`. Windows — собственный провайдер и подслой Windows Filtering Platform (WFP) с максимальным весом подслоя; фильтры разрешают loopback, локальные сети, DHCP, TUN и AppId ядра, блокирующий фильтр стоит ниже всех разрешений. `netsh advfirewall` не используется: в брандмауэре Windows блокирующие правила приоритетнее разрешающих, поэтому allow-list без смены глобальной политики не выражается. Рантайм Windows не проверялся (нет VM) — см. `S4-T5c`.
  - **Жизненный цикл.** Включение идемпотентно; ошибка применения возвращает `KILL_SWITCH_FAILED` и не запускает ядро. Если старт сорвался после установки правил этим же вызовом, они снимаются; правила, оставшиеся от прошлого падения, сохраняются. При старте helper'а «залипшие» правила прошлого запуска удаляются после захвата сокета. Выход приложения вызывает `stop`.
  - **Интерфейс.** Состояние (`enabled`/`error`) приходит в `HelperStatus.kill_switch`; если ядро упало при активной защите, UI показывает ошибку и кнопку «Отключить и снять защиту», а не «подключено».
- Внутренний DNS sing-box работает через TUN; политика DNS описана в §6.4.
- Конфиг, который получает helper: генерируется приложением, проходит `sing-box check`, пишется в root-каталог и удаляется при остановке.
- **Статистика трафика сессии.** Источник — локальный Clash API ядра (`experimental.clash_api`) на `127.0.0.1` и случайном свободном порту, со случайным `secret` на каждую сессию; наружу API не доступен. Приложение (непривилегированный процесс) читает `GET /connections` с `Authorization: Bearer <secret>` и берёт только суммарные `uploadTotal`/`downloadTotal`. Считается весь трафик, прошедший через ядро (через прокси и direct через TUN). Счётчики сбрасываются при новом `start`, после `stop` — нули. Ошибка чтения метрик не влияет на подключение: одно предупреждение в лог, в UI — «—». Серия не переживает перезапуск приложения: порт и `secret` живут в памяти.

### 6.3. Allowlist приложений (M4) — ключевая функция

**Честное определение.** Маршрутизация выполняется по процессу — владельцу сокета, а не по «приложению» в пользовательском смысле. Поэтому:

- `curl`, запущенный в Terminal, матчится как `curl`, а не как `Terminal`. Чтобы пустить через прокси все CLI-утилиты, нужно добавить конкретные бинари или правило по каталогу (например, `/opt/homebrew/bin/*`).
- Браузер создаёт несколько процессов (helper'ы), которые тоже делают сетевые соединения. Поэтому для браузеров используется правило по пути внутри `.app` (macOS) или по каталогу установки (Windows/Linux), а не только имя процесса.
- Приложения внутри Flatpak/Snap на Linux могут иметь путь внутри sandbox; такие правила помечаются как «может не сработать» и проверяются вручную.

**Модель правила.**

```json
{
  "id": "rule-chrome",
  "name": "Google Chrome",
  "platform": "macos",
  "process_name": ["Google Chrome", "Google Chrome Helper"],
  "process_path": ["/Applications/Google Chrome.app/Contents/MacOS/Google Chrome"],
  "path_regex": ["^/Applications/Google Chrome\\.app/"],
  "enabled": true
}
```

Используются те поля, которые поддерживает ядро на текущей ОС; `path_regex` — предпочтительный вариант для браузеров, `process_name` — для простых случаев и CLI.

| ОС | Основной идентификатор | Как получаем | Нюанс |
|---|---|---|---|
| macOS | абсолютный путь внутри `.app` | `NSRunningApplication`, обход `/Applications`, `/System/Applications`, `~/Applications` | helper-процессы требуют regex по каталогу `.app` |
| Windows | полный путь `.exe` | перечисление процессов, реестр, ярлыки Start Menu | Store-приложения (AppX) — после MVP; пути могут отличаться у разных установок |
| Linux | путь из `/proc/<pid>/exe` | `/proc`, `.desktop`-файлы | Flatpak/Snap — sandbox-пути; Wayland на матчинг не влияет |

- UI: вкладки «Запущенные / Установленные / Все правила». «Установленные» — каталог приложений ОС (v0.2, S4-T1): macOS — `.app` в `/Applications`, `/System/Applications`, `~/Applications` (один уровень); Linux — `.desktop` (путь из `Exec`); Windows — ярлыки «Пуск» и записи `Uninstall` с `DisplayIcon`. Поиск по имени, действие «Добавить правило» создаёт **выключенное** правило: macOS — `path_regex` по каталогу `.app`, Windows/Linux — `process_path`. Иконки (S4-T2) приходят отдельной командой `app_icon(app)` как готовый data URL: macOS — PNG-чанк из `.icns`, Linux — `Icon=` из `.desktop` с поиском в `hicolor`, Windows — ресурс `.exe`; изображение нормализуется до 64 px, кэшируется в памяти по пути. UI грузит иконку лениво по появлению строки и при её отсутствии показывает заглушку с первой буквой имени (не блокирует список и не читает диск на каждый рендер). «Запущенные» (S4-T11) — реальный список процессов ОС без привилегий и внешних команд (macOS — `proc_listpids`/`proc_pidpath`, Linux — `/proc/<pid>/exe`, Windows — Toolhelp): поиск по имени, «Обновить список», «Добавить правило» создаёт выключенное правило; системные и недоступные записи отбрасываются, дубликаты схлопываются по пути, список ограничен 500 строками и сортируется по имени, иконки в нём не запрашиваются. Ручное добавление пути — на вкладке «Все правила»; переключатель на каждое правило. Для типа «Regex по пути» рядом с формой кнопка (i) с шпаргалкой (S9-T4): удвоение `\` пути, экранирование точки, якоря `^…$` и замена каталога версии самообновляющегося приложения (Discord `app-1.0.9269`) на `app-[0-9.]+` — приложение меняет каталог при каждом своём обновлении, и правило по полному пути без этого ломается.
- Валидация: если пути нет на диске, правило сохраняется, но помечается «неактивно» с подсказкой (S4-T12). Проверка — локальный `stat` при чтении списка: `rules_list`, `rules_upsert` и `rules_delete` отдают `AppRuleView {…AppRule, missing_paths}`, без сети и привилегий. Проверяются только абсолютные `process_path` и regex, целиком сводящиеся к литеральному пути (`^<путь>/` — так их создаёт каталог); `process_name` и шаблоны с метасимволами не проверяются, при сомнении правило считается активным, ложного «неактивно» не бывает. Если существует хотя бы один проверяемый путь, правило активно. Признак не сохраняется в `state.json` и пересчитывается при каждом чтении; включение и удаление правила не блокируются. Отсутствие запущенного процесса ошибкой правила не считается. Каталог по-прежнему отбрасывает записи с отсутствующим `Exec` при сканировании Linux.
- UI показывает итоговый сгенерированный конфиг (без секретов) — для доверия и отладки.

### 6.4. DNS

- Цель: не допускать молчаливых утечек DNS выбранных приложений и дать пользователю выбор между приватностью и совместимостью.
- **Разделение DNS по процессу (бывший вариант по умолчанию) не поддерживается.** На macOS 15.8.2 / sing-box 1.14.4 DNS-правила с `process_name`/`process_path` для TUN не матчатся: `dns/tls[remote]` остаётся unreferenced, DNS выбранного приложения уходит в локальный resolver. Проверено 2026-11-12, подробности — `docs/research.md` §9. `hijack-dns` и `sniff` это не исправляют.
- **Пользователь выбирает один из двух режимов** в настройках; по умолчанию — `proxy`:
  - **`proxy` — весь DNS через прокси.** В sing-box остаются `remote` (DoT через `proxy`) и `local` (системный); включён `hijack-dns` для порта 53, `dns.final = remote`. Утечек нет, но DNS невыбранных приложений тоже идёт через прокси, а локальные имена (`.local`, captive portal) могут требовать отдельного правила `local`. Remote DoT через прокси проверен 2026-11-12.
  - **`system` — системный DNS для всех.** В конфиге только `local`, без `remote` и DNS-правил. Максимально совместимо, но DNS выбранных приложений уходит в локальный resolver; в UI показывается предупреждение.
- В UI: переключатель режима, короткое объяснение последствий каждого и предупреждение для `system`; в логах — выбранный режим и риск утечки для `system`. Молчаливых утечек быть не должно.
- Отдельный пункт проверки: DNS через TUN при активном `systemd-resolved` на Linux и при включённом Private Relay на macOS; локальные домены в режиме `proxy`.

### 6.5. Трей, автозапуск, окно (M6)

- Трей: иконка отражает состояние (отключено / подключение / подключено / ошибка), меню — статус, локация, подключить/отключить, открыть, выход.
- Закрытие окна сворачивает в трей (настраивается). Выход из трея корректно останавливает ядро и helper-сессию.
- Автозапуск: Tauri autostart plugin; опции «запускать свёрнутым» и «подключаться при старте».
- **Автоподключение при старте.** Настройка `preferences.connect_on_start` (по умолчанию выключена) применяется один раз при запуске приложения, в фоне: окно не ждёт helper'а и сети. Попытка выполняется тем же путём, что и кнопка «Подключить»; если сохранённой локации нет или ядро уже запущено, она пропускается без повторного `start`. Ошибка старта — штатное состояние «ошибка» с кодом на «Главной», приложение остаётся работоспособным; причина пишется в лог без адресов серверов и секретов. С включённым «запускать свёрнутым» автоподключение работает так же, только окно не показывается. После неудачной попытки ручное подключение и остальные экраны доступны; ошибка снимается при следующем подключении или отключении.
- Single instance: повторный запуск открывает существующее окно.

### 6.6. Настройки (M8)

- Подписки: список записей с полями имя, URL, User-Agent, интервал автообновления каждой (`0` — выключено) и кнопкой «Обновить» у записи; добавление и удаление — там же, удалённая подписка убирается вместе с кэшем. HWID — общий для всех подписок, редактируется в карте «Устройство». На «Локациях» у каждой группы видно, когда было последнее обновление и когда ждать следующее; при интервале `0` — «Автообновление выключено».
- Сеть: MTU, IPv6 (вкл/выкл), локальный mixed-inbound (вкл/выкл, порт по умолчанию 10808), DNS-режим: `proxy` (весь DNS через прокси, по умолчанию) или `system` (DNS ОС, с предупреждением об утечке).
- Безопасность: kill switch (fail-closed, по умолчанию выключен) — переключатель с предупреждением, что при обрыве туннеля прямой выход в интернет будет заблокирован до отключения. Настройка применяется при следующем подключении; состояние и ошибка правил видны на «Главной». Механизм платформенный (pf, nftables, WFP), набор исключений общий: loopback, локальная сеть, ядро, трафик TUN и DHCP.
- Локации: «автовыбор» (выбирать локацию с минимальной задержкой) и «автопереключение» при деградации. Обе настройки по умолчанию выключены. Порог деградации по умолчанию 100 мс, интервал проверки 60 с, подтверждений подряд 2, неудачных замеров до переключения 2. Диапазоны: порог 0…2000 мс, интервал 15…3600 с, подтверждений и неудач 1…5. Старые `state.json` без блока читаются с этими значениями (`#[serde(default)]`). Автопереключение работает только при активном подключении и явно включённой настройке; если новая локация не запускается, приложение возвращается к прежней.
- Приложение: язык интерфейса (русский/английский, применяется без перезапуска), автозапуск, старт свёрнутым, автоподключение, уровень логов, папка логов.
- **Обновления.** Канал `stable`/`beta`, проверка при запуске (opt-in), текущая версия, ручная проверка, установка с перезапуском. Проверка при запуске ничего не устанавливает: установка — только по явной кнопке. Артефакты подписываются minisign-ключом; приватный ключ хранится вне репозитория, в приложении — только публичный. Без действительной подписи установка отменяется. Установленный helper обновляется отдельно: если версия протокола изменилась, UI предлагает переустановить его из настроек. Хостинг манифеста — GitHub Releases (§13, п. 11); в debug-сборке база переопределяется `SPLITROUTE_UPDATE_ENDPOINT`.
- Язык — часть пользовательских настроек: `preferences.language` (`ru` по умолчанию) в `state.json`. Отсутствующее поле читается как `ru`, неизвестное значение — тоже `ru`, чтобы ручная правка файла не сбрасывала остальные настройки. Источник истины — Rust (AGENTS §10.8); UI переключает язык через `settings_update` и применяет его без перезапуска окна.
- Helper: статус (установлен / не установлен / устарел / не отвечает) с версией ядра, «установить»/«переустановить», «удалить». Ошибка установки показывается с конкретной причиной: нужны права, операция отменена, не найден бинарь, платформа не поддерживается. Пароль администратора запрашивает система, приложение его не хранит.
- Сброс настроек и очистка кэша подписки.

### 6.7. Логи и диагностика (M9)

- Просмотр последних N строк логов приложения и ядра, фильтр по уровню, автоскролл.
- «Копировать диагностику»: версия приложения, ОС, архитектура, версия sing-box, статус helper'а, выбранная локация, тип ошибки; без URL подписки, HWID и UUID.
- Ротация логов, ограничение размера.

### 6.8. Права и helper (M7)

- Первый запуск без helper'а: приложение работает в ограниченном режиме (подписка, настройки, список приложений), подключение недоступно.
- Установка helper'а — отдельный экран с объяснением, зачем нужны права, и одной кнопкой. Требуется пароль администратора / UAC / polkit; пароль вводится в системном диалоге и приложением не хранится.
- Если установка не удалась, UI показывает код и точную причину от установщика (`RequiresPrivileges`, отмена пользователем, отсутствующий бинарь, неподдерживаемая платформа), а не общую строку. Статус после действия берётся только из `helper_status`.
- Удаление helper'а — из настроек, полностью очищает сервис, сокет и runtime-файлы.
- Протокол helper'а (версия 2): только `install`, `uninstall`, `start`, `stop`, `status`. Никаких произвольных команд и путей. В `start` добавлен флаг `kill_switch`: он не передаёт правила, а только разрешает фиксированный набор, который helper ставит сам. В `status` добавлено состояние правил (`kill_switch.enabled`/`error`). Старый helper версии 1 несовместим осознанно: он проигнорировал бы флаг и оставил трафик без защиты; UI предлагает переустановку. Конфиг проверяется `sing-box check` до запуска.

## 7. UX

### Экраны

1. **Главная.** Большая кнопка подключения, текущая локация, время сессии, счётчики трафика ↑/↓ за сессию (КиБ/МиБ/ГиБ, обновление раз в секунду без перезагрузки окна; при недоступном источнике — «—» без `ErrorBox`), краткий статус (helper, DNS, количество приложений в allowlist, kill switch: активен/выключен/ошибка, автовыбор локации: выключен/включён/последняя проверка), быстрый переход к локациям. Если ядро упало при активном kill switch — явная ошибка и кнопка снятия защиты.
2. **Локации.** Локации сгруппированы по подпискам в порядке добавления: у каждой группы — имя (или «Подписка N» для безымянной), время последнего обновления, «Следующее обновление: …» (или «Автообновление выключено» при интервале `0`) и кнопка «Обновить» этой подписки. Внутри группы — список профилей с названием, протоколом, адресом сервера, задержкой и отметкой «выбрано». Кнопка «проверить задержки» общая: во время проверки — индикатор, после — миллисекунды или локализованный код ошибки, список сортируется по задержке (недоступные — в конце), лучшая локация помечается. Если включён автовыбор, лучшая локация выбирается после проверки. Ошибка загрузки подписки показывается внутри её группы. Пустое состояние — «добавьте подписку».
3. **Приложения.** Поиск, вкладки «Запущенные / Установленные / Все правила», переключатель «через прокси». Пояснение про процессы и дочерние процессы терминала. Ручное добавление пути. В каталоге установленных — иконка приложения и заглушка с первой буквой, если иконки нет; «Запущенные» показывает процессы ОС без иконок и с PID. На «Все правила» правило с отсутствующим на диске путём помечается «неактивно» с подсказкой, но остаётся доступным для включения и удаления.
4. **Настройки.** Группы из §6.6, включая переключатель языка интерфейса, явные подписи и подсказки, без «экспертных» полей без объяснения.
5. **Логи.** Моноширинный текст, уровни, копирование.

### Состояния и ошибки

- Не подключено / подключение / подключено / отключение / ошибка.
- Нет подписки, подписка не обновилась, пустая подписка.
- Helper не установлен / устарел / не отвечает.
- Конфликт с другим VPN или TUN-интерфейсом.
- Нет прав, нет сети, сервер недоступен, TLS-ошибка, несовместимый профиль.
- Каждая ошибка: что произошло, что сделать, кнопка «копировать диагностику».

### Дизайн

- Тёмная тема по умолчанию, светлая — после MVP.
- Референсы: Happ (простота и крупные акценты), FlClash (списки приложений), Clash Verge Rev (трей, настройки, статус ядра).
- Русские тексты, тон нейтральный, без технического жаргона там, где можно сказать проще.

## 9. Архитектура (обзор)

```
┌───────────────────────────┐
│ Tauri UI (React + TS)     │  окно, трей, экраны, i18n
└─────────────┬─────────────┘
              │ Tauri commands / events
┌─────────────▼─────────────┐
│ Rust core (непривилегир.) │  подписка, модель Profile, AppRule,
│                           │  генератор конфига, состояние, логи
└─────────────┬─────────────┘
              │ Unix socket / named pipe, JSON-протокол
┌─────────────▼─────────────┐
│ Privileged helper (root)  │  install/uninstall, start/stop, status;
│                           │  проверка конфига, запуск sing-box
└─────────────┬─────────────┘
              │ процесс
┌─────────────▼─────────────┐
│ sing-box (pinned sidecar) │  TUN, DNS, VLESS/Reality, process-правила
└───────────────────────────┘
```

Поток данных: `subscription JSON → Profile → (Settings + Profile + AppRule[]) → sing-box config → check → start`.

Обновления не участвуют в этом потоке: `tauri-plugin-updater` читает манифест `latest.json` выбранного канала (`stable`/`beta`), проверяет minisign-подпись артефакта и только по кнопке пользователя останавливает ядро, устанавливает обновление и перезапускает приложение.

Генератор конфига — чистая функция, покрытая golden-тестами. Точные поля конфига фиксируются под конкретную версию sing-box и проверяются `sing-box check`; пример ниже иллюстративный:

## 13. Принятые решения и открытые вопросы

### Принято

1. **Название — SplitRoute.** Идентификаторы пакетов и сервисов: `splitroute`. Финальные bundle id и домены фиксируются перед первой публичной сборкой.
2. **Лицензия — GPL-3.0.** Файл `LICENSE` в корне; сторонние компоненты и их лицензии — в `THIRD_PARTY_NOTICES` в корне. Оба файла входят в каждую сборку: macOS/Windows — ресурсы приложения, `.deb`/`.rpm`/AppImage — `/usr/share/doc/splitroute/`; DMG и NSIS показывают текст лицензии при установке. sing-box (GPL-3.0) поставляется как отдельный процесс без патчей, со ссылкой на исходники закреплённой версии.
3. **HWID — стабильный случайный идентификатор установки.** 16 hex-символов из CSPRNG, генерируется при первом запуске, хранится локально, отправляется в `X-HWID`, редактируется в настройках. Не строится из аппаратных серийников и MAC-адресов. Провайдер использует его как идентификатор устройства; смена HWID может сбросить привязку подписки.
4. **Kill switch — opt-in fail-closed в v0.2, не в MVP.** В MVP риск утечки при падении ядра признан (R13): детект, до 3 попыток переподключения и предупреждение. Автореконнект реализован (S4-T15, 2026-11-20): детект — фоновый надзор в Rust (раз в 2 с при активной сессии, работает и при закрытом окне), серия — до 3 попыток через общий путь подключения с паузой 3 с, при исчерпании — явное предупреждение `RECONNECT_FAILED` в UI; правила kill switch между попытками и при исчерпании сохраняются до ручного действия. В v0.2 добавлен выключенный по умолчанию kill switch для macOS (pf anchor), Linux (nftables) и Windows (WFP). Из-за отсутствия per-process firewall защита блокирует весь прямой выход непривилегированных процессов, а не только выбранных; локальная сеть исключена. На Windows выбран WFP, а не `netsh advfirewall`: брандмауэр Windows отдаёт приоритет блокирующим правилам, поэтому allow-list требует WFP-подслоя с весами; рантайм на Windows ещё не проверялся. Ручная проверка на реальных ОС — `S4-T5c`, живая проверка серии — research §32.
5. **DNS — два пользовательских режима.** Per-process DNS не поддерживается на macOS 15 / sing-box 1.14 (проверено 2026-11-12). Пользователь выбирает `proxy` (весь DNS через прокси, по умолчанию, без утечек) или `system` (DNS ОС, совместимо, но с предупреждением об утечке). Старый режим `process` выводится из UI и мигрирует в `proxy`.
6. **Автообновление — Tauri updater, установка только вручную.** Каналы `stable`/`beta`, манифест `latest.json`, подпись артефактов minisign. Проверка при запуске — opt-in, установка — только по кнопке с перезапуском приложения. Приватный ключ хранится вне репозитория, в конфиге только публичный; `requireSignedVersion` включён. Установленный helper обновляется отдельной переустановкой: сервис лежит вне бандла приложения.
7. **Доменные правила провайдера в MVP не переносятся (вариант A, 2026-11-14).** `geoip:ru`, `geosite:*` и direct-списки из шаблона скрипта в генерируемый конфиг не попадают. Причины: они ломают обещание «выбранное приложение целиком идёт через прокси» (часть трафика выбранного приложения уходила бы напрямую, мимо туннеля) и требуют `rule_set` (SRS-файлы) с внешним URL, то есть новую сетевую зависимость, кэш и обновление списков. Маршрут строится только из правил приложений и режима DNS (§6.3, §6.4). Умная маршрутизация возможна как отдельная фича после MVP — только явным переключателем в профиле и с предупреждением, что часть трафика выбранного приложения пойдёт напрямую.
8. **Несколько подписок — независимые записи с общим HWID (этап 6, 2026-11-19).** У каждой записи свои имя, URL, User-Agent и интервал автообновления; расписание ведётся по каждой (`fetched_at` записи + последняя попытка), попытка — включая ручную и неудачную — переносит следующее автообновление этой подписки на полный интервал. HWID один на устройство: провайдеру нужен идентификатор установки, и он не меняется от количества подписок. Активная локация одна на приложение; идентификатор профиля вычисляется из содержимого (имя, сервер, порт, UUID), поэтому совпадение между подписками возможно только для буквально одинаковых профилей. Загрузка ограничена «не больше одной на подписку» (разные подписки не блокируют друг друга), удаление подписки не трогает активный туннель, смена URL сбрасывает её кэш. Формат подписки (Happ-JSON/base64/vless) не зависит от количества подписок.
9. **Clash YAML — только VLESS-узлы (этап 7, 2026-11-20).** Подписка в формате Clash YAML распознаётся автоматически: YAML-отображение с ключом `proxies`; JSON-нотация и flow-стиль тоже принимаются (YAML — надмножество JSON). В модель профиля (§6.1) конвертируются только узлы `type: vless` с `network: tcp` и Reality/TLS: расширение до ss/vmess/trojan потребовало бы новых протоколов в ядре и генерации outbound'ов sing-box и выходит за рамки компактной задачи. Неподдерживаемые узлы пропускаются с причиной (как в Happ-JSON), пустой `proxies` — ошибка «пустой список», не-список — «неизвестный формат». Зависимость `serde_yaml` 0.9: зрелый минимальный serde-парсер; крейт в archive-статусе, но API заморожен, форки менее проверены. User-Agent подписки остаётся дискриминатором формата у провайдера; заголовок `Accept` не менялся, лимита тела подписки нет (ограничение — таймауты 45/10 с).
10. **Импорт по QR — декодер в Rust, только ссылка на подписку (этап 8, 2026-11-20).** Декодер — `rqrr` 0.11 (pure Rust): его опциональная зависимость `image` допускает 0.25, поэтому версии крейта в дереве не дублируются (image уже была через tauri/image-png). Альтернативы: `quircs` (binding к C — запасной вариант) и JS-декодер в вебвью (отклонён: парсинг форматов остаётся в Rust, canvas в jsdom не тестируется). Скоуз — только ссылка на подписку: запись требует URL (`subscription_add` отклоняет пустой), поэтому QR с голыми `vless://`-ссылками даёт ошибку, а не «статичную подписку без URL» — статичные записи потребовали бы правок стора, планировщика и этого PRD, это отдельное решение. Drag-drop — через оконное событие Tauri (`onDragDropEvent`): при включённом по умолчанию `dragDropEnabled` HTML5-события drop до страницы не доходят; paste — событие вебвью с image-элементом; правки capabilities не потребовались. Тесты декодера hermetic: dev-зависимость `qrcode` 0.14 рендерит QR в пиксели, PNG кодирует штатный `image` — граница между крейтами только PNG-байты, версии image не пересекаются.
11. **Релизы и хостинг манифеста обновлений — GitHub Releases (этап 9, 2026-11-22).** Релиз режется тегом `v*`: `release.yml` собирает Windows (NSIS) и Linux (AppImage) с updater-подписью из GitHub Secrets, создаёт черновик релиза с артефактами и `latest.json`, публикует после успешной загрузки — `releases/latest/download/<file>` раздаёт только опубликованные (не draft, не prerelease) релизы. Манифест канала — ассет последнего опубликованного релиза; ассеты GitHub плоские, поэтому канал кодируется именем файла: `latest.json` (stable) и `beta-latest.json` (beta), как в `updates.rs`. Поле `signature` манифеста — содержимое `.sig` как есть (CLI v2 пишет `.sig` одной строкой base64 от minisign-текста; плагин декодирует поле и парсит minisign-подпись), `requireSignedVersion` сверяет версию манифеста с `version:` из trusted comment подписи. deb/rpm апдейтером не используются и в манифест не попадают. Beta-тег (`*-beta*`) делает prerelease и дополнительно кладёт `beta-latest.json` на последний стабильный релиз, иначе beta-канал его не увидит; до первой beta-сборки beta-манифест ведёт на тот же релиз, что и stable. Свой домен — возможный будущий перенос, схема URL при нём меняется только в `updates.rs` и `tauri.conf.json`.

## Приложение A. Техническое исследование (кратко)

Полные ссылки и даты проверки — в [docs/research.md](./docs/research.md).

- sing-box поддерживает `process_name`, `process_path`, `process_path_regex` на Linux, Windows и macOS. Это основа per-app без своего packet-стека.
- Официальный Apple-клиент sing-box (SFM) не даёт process-правил из-за ограничений NetworkExtension; CLI-ядро с правами — даёт.
- На macOS 27 у не-Apple-подписанных бинарей чтение `pcblist` через sysctl возвращает только заголовок → process-правила не матчатся. Это главный риск архитектуры (R1).
- «Правильный» per-app на macOS — NetworkExtension (Packet Tunnel/App Proxy), требует entitlement и Apple Developer Program; переносим на этап 5.
- Текущая подписка: 2 профиля, оба `VLESS + Reality + TCP`; в outbound'ах также есть `direct`, `block`, `fragment-out`, в профиле — `burstObservatory`.
- Окружение разработки на текущей машине: macOS 15.8.2 arm64, Xcode CLT есть, Node 22 и pnpm есть, Rust отсутствует (устанавливается по AGENTS.md).
